# 프로젝트 코드 리뷰

목표는 **사용자에게 실제 버그로 나타날 문제**를 찾는 것이다. 취향 차이나 도구가 이미 잡는 문제를 늘어놓는 리뷰는 진짜 문제를 묻어 버린다. 발견 하나하나가 "이 상태에서 이렇게 하면 이렇게 틀린다"로 설명될 수 있어야 한다.

리뷰어는 코드를 고치지 않는다. 무엇을 고칠지는 리뷰를 요청한 쪽이 결정하니, 수정 방향만 구체적으로 제안한다.

## 프로젝트 한눈에 보기

| 파일 | 역할 |
|---|---|
| `index.html` | 화면 구조. `<script src="app.js" defer>` (classic script) |
| `style.css` | `:root` 컬러 토큰, 모바일 1열 → 768px 이상 2열 |
| `app.js` | 상수 → 저장소 → 날짜 유틸 → 후보 계산 → 원판 그리기 → 회전 → 결과 처리 → 메뉴/기록 → 렌더링 → 초기화 순서의 섹션 |
| `tests/app.test.mjs` | `node:test` 유닛 테스트. `loadApp()`이 가짜 DOM 위에 실제 app.js를 불러온다 |
| `tests/e2e.mjs` | headless Chrome으로 실제 화면 흐름 점검 |
| `scripts/build.mjs` | `dist/` 생성 + 참조 파일·`type="module"`·CDN 버전 고정 검사 |
| `eslint.config.mjs` | `innerHTML`·`insertAdjacentHTML`·`toISOString` 금지, `eqeqeq`, `prefer-const` |

## 1. 범위 정하기

- 요청에 파일·함수·커밋이 지정되어 있으면 그것만 본다.
- 지정이 없으면 git 변경분을 본다.
  - 커밋 직전 점검: `git diff --cached`
  - 일반: `git diff HEAD`와 `git status --porcelain`(새 파일 포함)
  - 아직 커밋이 하나도 없으면 `HEAD`가 없어 diff가 실패한다. 이때는 `git status`의 파일 목록 전체를 리뷰 대상으로 삼고, 그렇게 했다고 보고서에 적는다.
- 바뀐 줄만 보지 말고 **그 줄이 속한 함수 전체와 호출하는 쪽**까지 읽는다. 이 프로젝트의 버그는 대부분 새 코드와 기존 흐름(update → render, spin → finish)이 맞물리는 지점에서 생긴다.

## 2. 자동 검사 먼저

```bash
npm run lint && npm run build && npm test
```

- 결과를 보고서 맨 위에 요약한다. 실패가 있으면 그 자체가 🔴 발견이다.
- 린트가 잡는 문제(`innerHTML`, `toISOString`, `==` 등)는 따로 다시 보고하지 않는다. 리뷰어의 시간은 도구가 못 잡는 것에 쓴다.
- 회전·모달·레이아웃 같은 화면 흐름을 바꾼 변경이면 `npm run test:e2e`(약 25초)도 돌린다. Chrome이 없어서 못 돌렸다면 못 돌렸다고 적는다.
- `npm`이 없거나 `node_modules`가 없으면 `npm install` 없이 가능한 범위에서 리뷰하고, 자동 검사를 건너뛴 사실을 적는다.

## 3. 프로젝트 규칙 체크리스트

이 프로젝트를 만들면서 실제로 깨지기 쉬웠던 지점들이다. 변경과 관련된 항목을 중심으로 확인한다.

**file:// 실행 호환** — 사용자는 `index.html`을 더블클릭해서 연다.
- `<script type="module">`, `import`/`export`, 로컬 파일 `fetch()`는 file://에서 막힌다.
- 새 외부 스크립트는 CDN 주소에 정확한 버전을 고정하고, 로드에 실패해도 앱이 동작해야 한다(`typeof window.confetti === 'function'` 패턴).

**날짜는 로컬 기준** — 한국 시간 오전 9시 전에 UTC로 계산하면 날짜가 하루 밀린다.
- `toDateStr()`·`daysAgo()`를 쓴다. `new Date('2026-10-11')`처럼 날짜 문자열을 `Date`에 그대로 넣는 것도 UTC 자정으로 해석되니 피한다(`daysAgo`처럼 `split('-')`으로 나눠서 만든다).
- "최근 N일 제외"의 판정은 `daysAgo < N`이다. 경계값(N일 전에 먹은 메뉴는 후보에 포함)을 바꾸는 변경은 의도된 것인지 확인한다.

**사용자 입력은 textContent로만** — 메뉴 이름은 사용자가 입력한다.
- DOM은 `h()` 헬퍼나 `textContent`로 만든다. `title`·`aria-label`은 `setAttribute`라 안전하다.

**localStorage 방어** — 시크릿 모드나 차단 설정에서는 접근 자체가 예외를 던진다.
- 모든 접근은 `load()`/`save()`의 try/catch를 거친다.
- `load()`는 저장된 값의 모양을 검증한다. 저장 구조를 바꾸면 검증 로직도 같이 바꾸거나 키 버전(`lunchRoulette.v1`)을 올려야 한다. 안 그러면 기존 사용자의 데이터가 조용히 버려지거나 깨진 값이 들어온다.

**포인터와 당첨 결과 일치** — 이 앱의 핵심 신뢰 포인트다.
- `spin()`은 당첨 칸을 먼저 뽑고 회전각을 역산한다. `drawWheel()`의 칸 배치(12시부터 시계방향)와 `spin()`의 각도 계산은 같은 기준을 공유하므로, 한쪽만 바꾸면 화살표와 결과가 어긋난다.
- 회전 중에 `state.wheelItems`가 바뀌면 안 된다. 원판 칸을 바꾸는 경로(`update()`, `shuffle()`)가 회전 중에 호출될 수 있는지 본다.

**회전 중 잠금** — 필터·메뉴·기록 UI는 `.lock-group` fieldset 안에 있어서 회전 중에 통째로 비활성화된다.
- 후보를 바꾸는 새 컨트롤이 fieldset 밖에 있거나, 키보드·타이머 등 다른 경로로 실행될 수 있으면 `state.spinning` 확인이 필요하다.

**update()와 render() 구분**
- 데이터(`data.*`, `state.skipped`)를 바꿨으면 `update()`(저장 → 후보 재계산 → 원판 다시 뽑기 → 그리기 → 렌더)를 호출해야 한다. `render()`만 부르면 저장이 안 되거나 원판이 옛 후보를 보여준다.
- 화면만 바뀌는 경우에 `update()`를 부르면 원판 칸이 매번 다시 섞인다.

**공정성** — 모든 후보의 확률은 같아야 한다.
- `shuffled()`(Fisher–Yates)와 `Math.floor(Math.random() * n)`을 쓴다. `sort(() => Math.random() - 0.5)`는 편향된다.
- 후보가 12개를 넘으면 원판에는 12개만 올라간다. 원판 밖 후보가 계속 소외되지 않도록 후보가 바뀔 때·섞기·[다시] 때 다시 뽑는 흐름이 유지되는지 본다.

**빈 상태와 경계 상황**
- 후보 0개(카테고리 미선택 / 전부 제외), 후보 1개(원판 한 칸), 메뉴 이름 중복, 공백 이름, 긴 이름(원판 글씨 말줄임), 기록 100건 상한.

**접근성**
- 클릭 가능한 것은 `<button>`이다. 토글 칩은 `aria-pressed`, 아이콘 버튼(×)은 `aria-label`을 단다.
- 모달이 열리면 [먹을게요]에 포커스, 닫히면 [돌리기]로 돌아온다. Esc와 바깥 클릭으로 닫힌다.
- `prefers-reduced-motion`이면 회전이 짧아지고 꽃가루가 꺼진다.

**반응형·한글**
- 390px에서 가로 스크롤이 없어야 한다. 그리드는 `minmax(0, 1fr)`이다(canvas 고유 크기가 칼럼을 밀어내지 않게).
- 입력 요소 글자 크기는 16px 이상이다(iOS 자동 확대 방지). `word-break: keep-all`로 단어 중간 줄바꿈을 막는다.
- 한글 입력 중 Enter를 `keydown`으로 처리한다면 `e.isComposing`을 확인해야 마지막 글자가 두 번 들어가지 않는다.

**캔버스**
- 크기를 바꿀 때 `devicePixelRatio`를 반영하고, 리사이즈와 웹폰트 로드(`document.fonts.ready`) 뒤에 다시 그린다.

## 4. 발견을 검증하기

후보 발견마다 **구체적인 재현 시나리오**(어떤 입력·상태에서 → 어떤 잘못된 결과)를 만든다. 만들 수 없으면 버리거나 "확인 필요"로 분리한다.

- 이미 다른 곳에서 처리하고 있지 않은지 확인한다(fieldset 잠금, `load()` 검증, `finish()`의 중복 실행 방지 등).
- 로직 문제는 직접 돌려서 확인하면 확실하다. `tests/app.test.mjs`의 `loadApp()` 방식(가짜 DOM + `vm`)을 그대로 쓰면 브라우저 없이 app.js 함수를 호출할 수 있다. 확인용 스크립트는 프로젝트 폴더 밖(임시 폴더)에 만든다.
- 테스트가 없는 동작을 바꾼 변경이면, 어떤 테스트가 있어야 하는지 💡 제안으로 적는다.

## 5. 심각도

| 등급 | 기준 |
|---|---|
| 🔴 높음 | 앱이 안 뜸, 데이터 손실, 포인터와 결과 불일치, XSS, file://에서 깨짐, 자동 검사 실패 |
| 🟠 중간 | 특정 조건에서 오동작(날짜 경계, 빈 상태, 회전 중 조작), 모바일 레이아웃 깨짐, 키보드·스크린리더 사용 차단 |
| 🟡 낮음 | 작은 UX 문제, 유지보수를 어렵게 하는 구조, 사소한 성능 |
| 💡 제안 | 고치지 않아도 되는 개선, 추가하면 좋을 테스트 |

## 6. 보고 형식

아래 형식을 그대로 쓴다. 발견은 심각도 순으로, 많아도 10개 안쪽으로 추린다. 비어 있는 등급 섹션은 생략한다.

```markdown

**범위:** <파일 목록 또는 커밋> · **자동 검사:** lint ✅ / build ✅ / test ✅ 27/27 / e2e ⏭️ 건너뜀(UI 변경 없음)

### 🔴 높음
1. **<한 줄 요약>** — `app.js:123`
   - 문제: <무엇이 왜 틀렸는지>
   - 재현: <입력·상태> → <잘못된 결과>
   - 제안: <구체적인 수정 방향. 필요하면 짧은 코드>

### 🟠 중간
...

### 🟡 낮음
...

### 💡 제안
...

### 확인 필요
- <재현까지는 못 했지만 의심되는 점과, 확인하려면 무엇을 보면 되는지>

### 총평
<2~3문장. 이대로 커밋해도 되는지, 꼭 고쳐야 할 것이 무엇인지>
```

- 발견이 없으면 "발견 없음"이라고 쓰고, 무엇을 확인했는지(범위, 자동 검사, 체크리스트 중 본 항목)를 적는다. 억지로 채우지 않는다.
- 위치는 항상 `파일:줄`로 적는다. 줄 번호는 지금 파일 기준이다.
- 칭찬 섹션은 쓰지 않는다. 프로젝트 관례(한국어 주석, `h()` 헬퍼, 섹션 순서)와 다른 스타일 취향은 지적하지 않는다.
